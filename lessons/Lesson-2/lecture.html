1. Боль без Git: «final_v2_FINAL.html»

1. Pain without Git: "final_v2_FINAL.html"

Узнаёте? У всех начинающих разработчиков (и студентов, и дизайнеров, и копирайтеров) папки выглядят одинаково:

Recognize this? All beginners (developers, designers, copywriters) have folders that look the same:

project/ ├── index.html ├── index_v2.html ├── index_v3_NEW.html ├── index_FINAL.html ├── index_FINAL_FINAL.html ├── index_FINAL_FINAL_v2.html ├── index_FINAL_FINAL_v2_USE_THIS.html └── index — копия (3).html
project/ ├── index.html ├── index_v2.html ├── index_v3_NEW.html ├── index_FINAL.html ├── index_FINAL_FINAL.html ├── index_FINAL_FINAL_v2.html ├── index_FINAL_FINAL_v2_USE_THIS.html └── index — copy (3).html

Это «версионирование руками». Звучит безобидно, но в реальной работе оно приводит к катастрофам:

  • Не помните, что менялось. Через неделю смотрите на 8 файлов и не знаете, какие отличия в v3 от v2.
  • Случайно удалили рабочую версию. «А, это же черновик!» — оказалось, нет.
  • Команда работает поверх друг друга. Вы и коллега правите один файл — кто-то теряет правки.
  • Нет истории. Когда заказчик говорит «верните как было неделю назад» — а как было неделю назад, никто не помнит.
  • Нельзя откатиться. Сломали приложение в 23:00 пятницы — нет способа вернуться к рабочей версии.

This is "manual versioning". Sounds harmless but in real work it causes disasters:

  • You forget what changed. Week later you stare at 8 files and don't know what's different in v3 vs v2.
  • You delete the working version. "Eh, it was just a draft!" — turns out, no.
  • The team works on top of each other. You and a colleague edit the same file — somebody loses changes.
  • No history. Client says "roll back to a week ago" — and a week ago is nowhere to be found.
  • Can't roll back. Broke the app at 23:00 Friday — no way to revert to a working version.

Документ Google Docs. В Google Docs есть «История изменений»: можно увидеть кто и когда что поправил, и одним кликом откатиться. Все привыкли к этому в текстах. Git — это «История изменений» для кода. Только мощнее в 100 раз.

Google Docs document. Google Docs has "Version history": you can see who edited what and when, and roll back with one click. Everyone takes this for granted in text. Git is "Version history" for code. Only 100× more powerful.

2. Что такое Git и почему он везде

2. What Git is and why it's everywhere

Короткое определение: Git — это система контроля версий. Это программа, которая отслеживает изменения в файлах вашего проекта. После каждого «снимка» (commit) Git помнит: что изменилось, кто изменил, когда, и зачем (по комментарию).

Short definition: Git is a version control system. A program that tracks changes in your project files. After every "snapshot" (commit) Git remembers: what changed, who changed it, when, and why (from the message).

Машина времени для кода. Каждый коммит — это точка в прошлом, в которую можно вернуться. «Откати на вчера» = одна команда. «Покажи разницу между сегодняшним и недельным кодом» = одна команда. «Найди коммит, в котором появился этот баг» = одна команда.

Лента в Instagram. Каждый пост — отдельный момент. Можно скроллить назад, видеть кто что лайкнул, кто что комментировал. Git ведёт такую же ленту для вашего кода: каждый коммит — пост.

Time machine for code. Each commit is a point in the past you can return to. "Roll back to yesterday" = one command. "Show me the diff between today's and last week's code" = one command. "Find the commit that introduced this bug" = one command.

Instagram feed. Each post is a separate moment. You can scroll back, see who liked, who commented. Git keeps the same feed for your code: each commit = a post.

Git создал Линус Торвальдс — тот самый, который придумал Linux. История: в 2005 году разработчики ядра Linux поссорились с владельцами проприетарной системы версий BitKeeper. Линус сказал: «Хорошо, я напишу свою за две недели». И написал. Назвал в честь британского сленгового слова git, что переводится как «дурак» — Линус про себя. Сегодня Git используется в 95% всех IT-проектов мира.

Git was created by Linus Torvalds — the same guy who invented Linux. The story: in 2005 Linux kernel devs fell out with the owners of the proprietary BitKeeper VCS. Linus said: "Fine, I'll write my own in two weeks". And he did. Named it after the British slang word git meaning "idiot" — referring to himself. Today Git is used by 95% of all IT projects worldwide.

Git — это не GUI-программа с окошками. Это командная строка: вы пишете команды вроде git commit -m "fix bug". Есть графические надстройки (GitHub Desktop, GitKraken, Sourcetree, встроенный Source Control в VS Code), но если вы серьёзно учитесь — учите команды. На любом собеседовании спросят «как сделать commit через терминал», а не «куда нажать в Sourcetree».
Git is not a GUI program with windows. It's a command line: you type commands like git commit -m "fix bug". There are GUI wrappers (GitHub Desktop, GitKraken, Sourcetree, VS Code's built-in Source Control), but if you're serious — learn the commands. Any interview asks "how do you commit from the terminal", not "where do you click in Sourcetree".

Это самая частая путаница новичков. Запомните раз и навсегда: Git и GitHub — это разные вещи.

The most common beginner confusion. Memorize once and for all: Git and GitHub are different things.

Word и Google Drive. Word — программа на компьютере (как Git). Google Drive — облако в интернете, где вы храните Word-файлы (как GitHub). Можно пользоваться Word без Google Drive — но нельзя загрузить файл в облако без какой-то программы. То же самое с Git и GitHub: Git нужен всегда, GitHub — для шаринга.

Word and Google Drive. Word is a program on your computer (like Git). Google Drive is the cloud where you store Word files (like GitHub). You can use Word without Drive — but can't upload a file to the cloud without a program. Same with Git and GitHub: Git is always needed, GitHub — for sharing.

Зачем разработчику GitHub-аккаунт:

  • Резюме. На любом собеседовании первым делом смотрят github.com/ваш-юзернейм. Профиль = ваше портфолио.
  • Совместная работа. Команда из 5 человек на одном проекте — без GitHub невозможно.
  • Open Source. Найти хорошие проекты, поучиться, сделать первый PR (Pull Request) — путь в индустрию.
  • Бэкап. Сломался ноутбук — код жив, у вас на GitHub.
  • Деплой. Бесплатные хостинги (Vercel, Netlify, GitHub Pages) подключаются прямо к репозиторию.

Why a developer needs a GitHub account:

  • Resume. Every interview starts with github.com/your-username. The profile is your portfolio.
  • Collaboration. A team of 5 on one project — impossible without GitHub.
  • Open Source. Find good projects, learn, make your first PR (Pull Request) — the way into the industry.
  • Backup. Laptop dies — code is alive on GitHub.
  • Deploy. Free hosts (Vercel, Netlify, GitHub Pages) connect directly to a repo.

Личный пример. Я (преподаватель) попал в open-source-сообщество Supabase именно через GitHub: нашёл небольшую проблему в их JS-библиотеке, прислал PR, его смержили — и моё имя теперь в списке контрибьюторов supabase/supabase-js. То же самое потом сделал в Hyperledger Identus, Medusa, phpReport. GitHub-история на момент собеседования говорит работодателю в 100 раз больше, чем диплом.

Personal example. I (the instructor) got into the Supabase open-source community via GitHub: found a small bug in their JS library, sent a PR, it got merged — my name is now in the contributor list of supabase/supabase-js. Then did the same in Hyperledger Identus, Medusa, phpReport. GitHub history at interview time tells an employer 100× more than a diploma.

4. Основные понятия: репозиторий, commit, history, branch

4. Core concepts: repository, commit, history, branch

Прежде чем писать команды — освоим словарь. 80% всех вопросов по Git на собеседовании — это знание этих 5 слов.

Before writing commands — let's learn the vocabulary. 80% of Git interview questions come down to knowing these 5 words.

Книга. Репозиторий = книга. Коммит = страница (с датой и подписью автора). История = последовательность страниц от 1-й до последней. Ветка = параллельный том («альтернативная концовка»). Remote = копия книги в библиотеке. Push = отправить новые страницы в библиотеку. Pull = забрать новые страницы из библиотеки.

A book. Repository = the book. Commit = a page (with a date and author's signature). History = the sequence of pages from 1 to last. Branch = a parallel volume ("alternative ending"). Remote = a copy of the book in the library. Push = send new pages to the library. Pull = grab new pages from the library.

В нашем курсе мы пока не работаем с ветками и pull request'ами — это тема более продвинутых уроков. Сегодня — только: создал репо → коммитим → пушим. Этого достаточно для всего следующего месяца.
In our course we don't work with branches and pull requests yet — that's a topic for more advanced lessons. Today only: created a repo → commit → push. Enough for the next month.

5. Установка Git и базовая настройка

5. Installing Git and base config

Windows:

Windows:

  1. Открыть в браузере: git-scm.com
  2. Большая кнопка «Download for Windows» → скачается .exe-инсталлятор (актуальная версия в 2026 — Git 2.46+)
  3. Запустить инсталлятор. Жмите «Next» с дефолтами на всех экранах. Дефолты Git подобраны хорошо.
  4. Один важный момент: на шаге «Choosing the default editor» можно выбрать Visual Studio Code (если уже установлен) — это удобнее, чем стандартный Vim.
  5. Установка длится 1-2 минуты. Никаких галочек снимать не нужно.
  6. После установки в Пуске появится «Git Bash» — это терминал, в котором мы будем запускать Git-команды. Также Git становится доступен в обычном PowerShell и CMD.
  1. Open in browser: git-scm.com
  2. Big button "Download for Windows" → an .exe installer downloads (current version in 2026 — Git 2.46+)
  3. Run the installer. Click "Next" with defaults on every screen. Git's defaults are well-chosen.
  4. One important note: on the "Choosing the default editor" step you can pick Visual Studio Code (if installed) — more convenient than the default Vim.
  5. Install takes 1-2 minutes. No checkboxes to uncheck.
  6. After install, "Git Bash" appears in the Start menu — that's the terminal where we'll run Git commands. Git is also available in regular PowerShell and CMD.

macOS:

macOS:

На современных Mac Git уже установлен. Проверьте: откройте Terminal → git --version. Если показывает версию — всё готово. Если предложит установить «Command Line Tools» — согласитесь.

Альтернатива через Homebrew: brew install git (даёт самую свежую версию).

On modern Macs Git is preinstalled. Check: open Terminal → git --version. If it shows a version — done. If it offers to install "Command Line Tools" — agree.

Alternative via Homebrew: brew install git (gives the latest version).

Базовая настройка (одна на всю жизнь):

Base config (one-time, forever):

Git должен знать, кто вы — чтобы подписывать ваши коммиты. Откройте терминал (Git Bash на Windows / Terminal на Mac) и выполните две команды:

git config --global user.name "Ваше Имя"
git config --global user.email "your_email@example.com"

Важно: email должен совпадать с тем, что вы укажете при регистрации на GitHub. Иначе ваши коммиты не будут связаны с вашим профилем (в счётчике активности они не отобразятся).

Проверка:

git config --global user.name      # должно показать ваше имя
git config --global user.email     # должно показать ваш email

Эту настройку делаете один раз — она применится ко всем будущим репозиториям на этом компьютере.

Git needs to know who you are — to sign your commits. Open the terminal (Git Bash on Windows / Terminal on Mac) and run two commands:

git config --global user.name "Your Name"
git config --global user.email "your_email@example.com"

Important: the email must match the one you'll use to register on GitHub. Otherwise your commits won't link to your profile (won't show up in the activity counter).

Verify:

git config --global user.name      # should show your name
git config --global user.email     # should show your email

You set this once — it applies to all future repositories on this computer.

Установить main как ветку по умолчанию (новые проекты будут начинать с main вместо устаревшего master):

git config --global init.defaultBranch main

Set main as the default branch (new projects start with main instead of the legacy master):

git config --global init.defaultBranch main

6. Аккаунт на GitHub: оформление профиля

6. GitHub account: setting up the profile

GitHub-аккаунт — это лицо разработчика в интернете. На него смотрит каждый рекрутёр. Уделите 15 минут на нормальное оформление — окупится сторицей.

A GitHub account is the developer's face online. Every recruiter looks at it. Spend 15 minutes setting it up properly — it pays back tenfold.

Регистрация:

Registration:

  1. github.com → «Sign up» в правом верхнем углу
  2. Email → тот же, что в git config user.email (это критично!)
  3. Пароль (минимум 15 символов или 8 с цифрой)
  4. Username → выберите осмысленно: это будет ваш URL (github.com/username) и часть портфолио. Хорошо: seydicharyev, aman-dev. Плохо: xxxgamer228, cool-boy-99.
  5. Подтвердите email (письмо из GitHub)
  6. Скип «Plan» → выберите Free
  1. github.com → "Sign up" top right
  2. Email → the same you put in git config user.email (critical!)
  3. Password (15+ chars or 8 with a digit)
  4. Username → pick mindfully: this will be your URL (github.com/username) and part of your portfolio. Good: seydicharyev, aman-dev. Bad: xxxgamer228, cool-boy-99.
  5. Verify email (letter from GitHub)
  6. Skip "Plan" → choose Free

Оформление профиля (15 минут на всю карьеру):

Profile setup (15 minutes for the whole career):

  1. Settings (правый верхний угол → Settings) → Profile
  2. Name: ваше реальное имя (как в паспорте, латиницей)
  3. Bio: 1-2 предложения о себе. Пример: «Front-end developer learning React. Based in Ashgabat 🇹🇲».
  4. Location: Ashgabat / Mary / ваш город
  5. Avatar: загрузите фото. Без фото профиль выглядит «полу-готовым» и не вызывает доверия.
  6. Сохраните → откройте свой профиль (github.com/username) → проверьте, что всё аккуратно.

10. Vite: что под капотом

10. Vite: what's under the hood

Мы уже сравнивали Vite и CRA на занятии 1. Сейчас углубимся: что именно делает Vite, когда вы запускаете npm run dev.

We compared Vite and CRA on lesson 1. Now let's dive deeper: what exactly does Vite do when you run npm run dev.

Что делает Vite: 1. Запускает локальный dev-сервер (по умолчанию http://localhost:5173) 2. Перехватывает запросы браузера к JS-файлам: - Компилирует JSX → обычный JS (через esbuild — на порядок быстрее Babel) - Преобразует import'ы для браузера - Возвращает готовый JS файл 3. Hot Module Replacement (HMR): - Меняешь App.jsx → Vite перекомпилирует только этот файл - Браузер обновляет компонент БЕЗ перезагрузки страницы - Сохраняется state (например, открытое модальное окно) 4. По команде "npm run build": - Собирает оптимизированный бандл в папку dist/ - Минифицирует, шейкает дерево (убирает мёртвый код) - Готов к деплою на любой статический хостинг
What Vite does: 1. Starts a local dev server (default http://localhost:5173) 2. Intercepts browser requests for JS files: - Compiles JSX → plain JS (via esbuild — orders of magnitude faster than Babel) - Transforms imports for the browser - Returns the ready JS file 3. Hot Module Replacement (HMR): - Edit App.jsx → Vite recompiles only that file - Browser updates the component WITHOUT a page reload - State is preserved (e.g. an open modal) 4. On "npm run build": - Builds an optimized bundle into dist/ - Minifies, tree-shakes (drops dead code) - Ready to deploy on any static host

Шеф-повар в ресторане. Вы заказываете блюдо (запрашиваете JS-файл из браузера). Шеф (Vite) готовит его прямо в момент заказа и приносит свежим. Когда вы меняете рецепт (правите код) — шеф автоматически переделывает только это блюдо, не перезаписывая весь ресторан.

Restaurant chef. You order a dish (request a JS file from the browser). The chef (Vite) cooks it at the moment of ordering and serves it fresh. When you change the recipe (edit code) — the chef automatically remakes only that dish, not the whole restaurant.

13. Dev-сервер и hot reload

13. Dev server and hot reload

Самая впечатляющая фишка Vite — мгновенное обновление при изменении кода. Покажу на пальцах.

Vite's most impressive feature — instant updates on code changes. Let me show you.

  1. В работающем проекте (npm run dev запущен) откройте src/App.jsx
  2. Найдите строчку <h1>Vite + React</h1>
  3. Поменяйте на <h1>Привет, мир!</h1>
  4. Сохраните файл (Ctrl+S)
  5. Посмотрите в браузер: заголовок изменился без перезагрузки страницы. Если в URL или в консоли что-то было — оно осталось.
  6. Кликните несколько раз на счётчик «count is 0», доведите до 5
  7. Поменяйте текст кнопки в коде, сохраните
  8. В браузере текст обновился, но счётчик остался на 5 — это и есть Hot Module Replacement (HMR). Состояние компонента сохранилось.
  1. In the running project (npm run dev active) open src/App.jsx
  2. Find the line <h1>Vite + React</h1>
  3. Change it to <h1>Hello, world!</h1>
  4. Save the file (Ctrl+S)
  5. Look at the browser: the heading updated without a page reload. If anything was in the URL or console — it stayed.
  6. Click the "count is 0" button several times, get to 5
  7. Change the button text in code, save
  8. In the browser the text updated but the counter is still at 5 — that's Hot Module Replacement (HMR). Component state preserved.
Это и есть «современная разработка»: вы видите результат изменений за миллисекунды. После Vite возвращаться к классическому «сохранил → F5 → жди загрузки» — невозможно.
This is "modern development": you see results in milliseconds. After Vite, returning to the classic "save → F5 → wait for load" is unthinkable.

14. Push на GitHub за 5 минут

14. Push to GitHub in 5 minutes

Проект работает локально. Теперь — выложим на GitHub. Это последний шаг, который превращает «папку на компьютере» в «публичный портфолио-проект».

The project works locally. Now — push it to GitHub. The last step that turns a "folder on your computer" into a "public portfolio project".

Шаги:

  1. В корне проекта (там, где package.json) откройте терминал. Vite уже создал репозиторий через git init автоматически — но если нет, выполните: 
    git init
git branch -M main
  2. Первый коммит: 
    git add .
git commit -m "Initial commit: Vite + React starter"
  3. На github.com: правый верхний угол → + → New repository
    • Repository name: my-first-react (то же, что и локальная папка)
    • Description: «My first React project (Vite + React 19)»
    • Visibility: Public
    • НЕ ставьте галочки «Add README» / «Add .gitignore» — они уже есть в проекте
    • «Create repository»
  4. На странице созданного репо найдите HTTPS URL (например, https://github.com/USERNAME/my-first-react.git) и скопируйте.
  5. В терминале: 
    git remote add origin https://github.com/USERNAME/my-first-react.git
git push -u origin main
  6. Git попросит Username (ваш GitHub-юзернейм) и Password — вставьте Personal Access Token, который создавали в шаге 7. Не пароль от аккаунта.
  7. Git закэширует токен. В браузере обновите страницу репо на GitHub — увидите все файлы проекта.

Steps:

  1. In the project root (where package.json is) open the terminal. Vite already ran git init automatically — but if not, run: 
    git init
git branch -M main
  2. First commit: 
    git add .
git commit -m "Initial commit: Vite + React starter"
  3. On github.com: top right → + → New repository
    • Repository name: my-first-react (same as the local folder)
    • Description: "My first React project (Vite + React 19)"
    • Visibility: Public
    • DON'T tick "Add README" / "Add .gitignore" — they already exist in the project
    • "Create repository"
  4. On the new repo page find the HTTPS URL (e.g. https://github.com/USERNAME/my-first-react.git) and copy it.
  5. In the terminal: 
    git remote add origin https://github.com/USERNAME/my-first-react.git
git push -u origin main
  6. Git asks for Username (your GitHub username) and Password — paste the Personal Access Token from step 7. Not the account password.
  7. Git caches the token. Reload the repo page on GitHub — you'll see all project files.

git add .
git commit -m "Add header component"
git push

За месяц практики эти 3 команды у вас войдут в мышечную память.
